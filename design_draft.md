## Overview

B2B-сервис для научных лабораторий, НИИ и R&D-подразделений: подбор проверенных аналогов оптических компонентов и их поставка через подтверждённые каналы. Клиент оставляет сложный закупочный запрос; инженер сервиса вручную подбирает варианты, готовит документированное сравнение характеристик, подтверждает цену и срок у поставщика и оформляет коммерческое предложение (КП). Это инженерно-коммерческий сервис с цифровой базой компонентов, а не автоматический маркетплейс.

## The Problem

Лаборатории не могут получить нужный оптический компонент: артикул недоступен, совместимость замены технически неочевидна (покрытия, допуски, качество поверхности), сроки поставки не подтверждены, комплектация закупки трудоёмка. Существующие дистрибьюторы (Azimut Photonics, ЛЛС) уже делают подбор аналогов, поэтому ценность проекта — не каталог, а качество процесса: документированное сравнение вариантов, проверенный канал поставки, подтверждённые цена и срок, контроль исполнения.

Решение: сайт с формой запроса, личным кабинетом клиента, внутренней базой компонентов/поставщиков и CRM для ручной обработки заявок инженерами.

## Goals

*   Принимать запросы на компоненты с вложениями (спецификация, чертёж) через веб-форму.
*   Давать клиенту личный кабинет: история запросов, статусы, полученные КП.
*   Вести внутреннюю базу компонентов (цель MVP: 100–300 позиций) с параметрами, документами и связями аналогов с уровнем достоверности.
*   Обрабатывать заявки в CRM-воронке: получен → уточнение → поиск → проверка характеристик → запрос поставщику → предложение → заказ → доставка.
*   Формировать техническое сравнение (совпадения / отличия / неизвестные параметры со ссылками на документы) и КП; отслеживать заказы.
*   Первый ответ по стандартному запросу — не более одного рабочего дня (организационная цель пилота).

## Non-Goals

*   Публичный каталог компонентов (база внутренняя; публичный каталог — после подтверждения спроса).
*   Автоматические рекомендации замен без инженерной проверки.
*   Собственный склад и лаборатория испытаний.
*   Интеграции с ЕИС/госзакупками, платёжные шлюзы, онлайн-оплата.
*   Email-рассылки и маркетинговые automation (уведомления — точечно, позже).
*   Очереди задач (Celery), полнотекстовый поисковый движок, микросервисы.
*   Мобильные приложения.

## Open Questions

*   **Доступ к локальной БД**: пользователь выбрал PostgreSQL 17 (порт 5433), пароль пользователя `postgres` не предоставлен; стандартный `postgres` не подошёл. Блокирует проверку `/health/db` и миграций.
*   **PDF-генерация**: WeasyPrint требует системных зависимостей (GTK/Pango на Windows). Локально на Windows возможен отказ; в Docker (linux) работает штатно. Решение: генерация PDF только в Docker-окружении либо fallback на HTML-версию сравнения.
*   **Уведомления клиенту о смене статуса**: на MVP клиент смотрит статус в кабинете; нужна ли email-нотификация хотя бы о готовности КП — решить после первых заявок.
*   **Состав полей формы запроса**: черновой набор согласован (артикул, производитель, тип, характеристики, количество, срок, вложение, контакты); уточнить по первым реальным заявкам.

## Critical User Journeys (CUJs)

### CUJ 1: Подача запроса

*   **Given**: Новый пользователь — инженер лаборатории; у него есть артикул нужного компонента и спецификация в PDF.
*   **When**: Регистрируется (организация, контактное лицо, email, пароль), входит, заполняет форму запроса, прикладывает PDF, отправляет.
*   **Then**: Запрос создан со статусом «получен», виден в личном кабинете; файлы вложений сохранены; админ видит заявку в CRM.

### CUJ 2: Обработка заявки инженером

*   **Given**: В CRM есть заявка со статусом «получен»; пользователь с ролью engineer/admin вошёл в админку.
*   **When**: Инженер переводит заявку по воронке, уточняет требования, ищет варианты в базе компонентов, запрашивает условия у поставщика, фиксирует предложение поставщика (цена, срок, MOQ).
*   **Then**: Каждое изменение статуса записано в историю; к заявке привязаны найденные компоненты и предложения поставщиков.

### CUJ 3: Сравнение и КП клиенту

*   **Given**: По заявке найдены 1–3 варианта замены с документами.
*   **When**: Инженер создаёт сравнение: исходный компонент и критические параметры, таблица совпадений/отличий/неизвестных, уровень достоверности каждого аналога (сопоставим по документации / кандидат / проверен в системе), ссылки на документы; формирует КП с ценой и сроком.
*   **Then**: Клиент видит КП в личном кабинете; статус заявки — «предложение»; документ сравнения доступен для скачивания.

### CUJ 4: Заказ и поставка

*   **Given**: Клиент принял КП.
*   **When**: Инженер создаёт заказ из КП, переводит заявку в «заказ», затем «доставка», фиксирует фактические сроки.
*   **Then**: История заказа и фактические сроки сохранены; данные пополняют рейтинг надёжности поставщика.

### CUJ 5: Повторный визит клиента

*   **Given**: Клиент ранее подавал запросы.
*   **When**: Входит в личный кабинет.
*   **Then**: Видит все свои запросы, текущие статусы, историю и КП; может подать новый запрос.

## Technical Plan (Architecture)

Один репозиторий, два приложения. Монолит FastAPI + один React SPA (публичные страницы, кабинет и админка в одном приложении, админка под `/admin` с проверкой роли). Выбрано для команды 1–3 человека и MVP-объёма.

```text
frontend/  React 18 + TypeScript + Vite + Tailwind CSS
           React Router · TanStack Query · React Hook Form + Zod
backend/   FastAPI · SQLAlchemy 2.0 (async, asyncpg) · Alembic · Pydantic v2
           JWT (access/refresh) · роли client/engineer/admin · pytest
postgres   PostgreSQL 16 (Docker) / 17 (локально)
files/     uploads: спецификации, datasheets, сгенерированные PDF
```

Поток данных: форма запроса → `POST /api/v1/requests` (multipart) → PostgreSQL + файловое хранилище → CRM админки → сравнение/КП → кабинет клиента.

Модель данных:

*   `User` — email, пароль (bcrypt/argon2), организация, контактное лицо, роль (client/engineer/admin).
*   `Request` — FK клиент, артикул, производитель, тип компонента, характеристики (текст/JSONB), количество, желаемый срок, статус, timestamps.
*   `RequestAttachment` — FK заявка, имя файла, путь, MIME, размер.
*   `RequestStatusHistory` — FK заявка, старый/новый статус, автор, комментарий, timestamp.
*   `Component` — артикул, производитель, тип (линза/зеркало/фильтр/…), типизированные поля для фильтров (диапазон длин волн, диаметр и т.п.) + JSONB для остальных параметров.
*   `ComponentDocument` — FK компонент, тип документа, ссылка/файл.
*   `AnalogRelation` — component ↔ analog, уровень достоверности (documented/candidate/tested), обоснование, подтверждающие документы.
*   `Supplier` — название, канал (производитель/дистрибьютор/иной), контакты, условия, рейтинг надёжности.
*   `SupplierOffer` — FK поставщик + компонент, цена закупки, срок, MOQ, дата подтверждения, история исполнения.
*   `Quote` + `QuoteItem` — FK заявка, цена, срок действия, статус.
*   `Order` — FK КП, фактические сроки, статус.
*   `ComparisonReport` — FK заявка, данные сравнения (JSONB), PDF-файл.

API (`/api/v1`): `auth/` (register, login, refresh, me), `requests/` (клиентские CRUD + вложения), `admin/requests/`, `admin/components/`, `admin/suppliers/`, `admin/analogs/`, `admin/quotes/`, `admin/orders/`, `admin/comparisons/`.

Ключевые решения:

*   Параметры компонентов: типизированные индексируемые поля + JSONB — гибкость для разнородной оптики без EAV.
*   Клиентские аккаунты с личным кабинетом (решение пользователя) — основа для продукта «регулярное снабжение».
*   Админка — раздел того же React SPA, защита JWT + роль; отдельный админ-стек не вводится.
*   Подбор аналогов — только ручной; статус «проверен в системе» присваивается лишь при наличии протокола испытаний.
*   Уровни достоверности аналогов хранятся явно и показываются клиенту в сравнении.

## Alternatives Considered

### Alternative A: Публичный каталог-маркетплейс с автоподбором

*   **Pros**: выглядит полноценнее, самообслуживание клиентов.
*   **Cons**: копирует конкурентов (Azimut, ЛЛС) без преимущества; автозамена без инженерной проверки создаёт техническую ответственность; индексация тысяч позиций до подтверждения спроса.
*   **Reason for Rejection**: отвергнуто пользователем по итогам исследования рынка; MVP проверяет спрос на обработку сложных запросов.

### Alternative B: Готовая админка (SQLAdmin)

*   **Pros**: CRUD из коробки, быстрее старт.
*   **Cons**: кастомная CRM-воронка, сравнения и КП требуют существенных доработок; второй стек и стиль.
*   **Reason for Rejection**: отвергнуто пользователем — своя админка на React в едином SPA.

### Alternative C: Без регистрации клиентов (отслеживание по токену из письма)

*   **Pros**: меньше трения, меньше кода.
*   **Cons**: нет истории и повторных заказов — базы для продукта №3.
*   **Reason for Rejection**: отвергнуто пользователем в пользу личного кабинета.

## Non-Functional Requirements

*   **Безопасность**: хеширование паролей bcrypt/argon2; JWT access (30 мин) + refresh (14 дней); проверка ролей на всех `/admin/*` эндпоинтах; валидация загрузок (MIME-список, лимит 20 МБ, хранение вне webroot); CORS whitelist; секреты только через `.env`; клиент видит только свои заявки.
*   **Производительность**: MVP-нагрузка мала (десятки заявок в день); пагинация списков; индексы на FK и полях фильтрации компонентов. Целевых SLA latency нет.
*   **Rollout & Rollback**: миграции Alembic (upgrade/downgrade); деплой Docker Compose на VPS; откат — предыдущий образ + `alembic downgrade`. Feature flags не вводятся.
*   **Данные**: персональные данные клиентов (email, контактные лица) — минимальный набор; экспорт/удаление по запросу — вручную на MVP.
